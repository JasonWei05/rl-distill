# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A fork of [`verl-project/verl`](https://github.com/verl-project/verl) used as a research codebase
("rl-distill") for RL training and distillation of **Gemma 3** (dense, dense→MoE upcycled, PT/IT)
and **Gemma 4** (E2B, E4B, 12B, 26B-A4B MoE) on **B200 / H100**. The active workstream is Gemma 4:
RL'd teachers per DeepScaleR difficulty band (easy/medium/hard) are distilled into base students
and compared against direct RL.

- `rl-distill-scripts/` holds almost all fork-specific work: launchers, docs, and custom code
  (datasets, losses, MoE converter, trace pipeline, eval harnesses). The busiest subdirectories are
  `scale_train/` (cluster jobs) and `data/` (data and trace tooling).
- `dapo/` is the RL entry-point package. Most of it is symlinks into `rl-distill-scripts/` (see
  below).
- `verl/` is the upstream framework. The fork now edits it substantively (see
  [fork changes](#fork-changes-in-verl)).
- Submodules are **not initialized in a fresh clone**; run `git submodule update --init <path>`.
  They are `lm-evaluation-harness` (unmodified EleutherAI, run standalone for evals), `recipe`
  (verl-recipe), and `third_party/nemo-rl` (only for `rl-distill-scripts/nemo_rl_repro/`, an
  exact NeMo-RL re-run of a verl Gemma 4 run used as a cross-framework parity check).
  `third_party/Megatron-Bridge` is vendored, not a submodule.

**Read the doc for an area before changing it.** The docs record the contracts and incident history
the code depends on. All are under `rl-distill-scripts/`:

| Doc | Role |
|---|---|
| `DISTILLATION_EXPERIMENTS.md` | **Live Gemma 4 ledger**, in `§N` sections: §2 traces, §4 recipe, §7 eval suite, §8 results (auto-generated by `update_distill_study_results_doc.py`), §9.x follow-up runs. A commit message prefixed `§9.0h: …` updates that section. |

## Three isolated environments — do not mix them

Each stack has incompatible pins and its own venv at the repo root. With the wrong venv, the
`vllm`/`transformers`/`torch` versions fail at import or at model load.

| Venv | Built by | Stack | Used for |
|---|---|---|---|
| `.venv` | `rl-distill-scripts/setup_env.sh` | torch 2.9.1+cu128, vllm 0.15.1, transformers 4.57.6, flash-attn 2.8.3 (built) | Gemma 3 FSDP2 RL and distillation |
| `.venv-megatron` | `setup_megatron.sh` | torch 2.10+cu129, vllm 0.18.0, transformers 5.3.0, Megatron-Core v0.16.0, TransformerEngine v2.12, vendored Megatron-Bridge | Gemma 3 Megatron RL, incl. MoE |
| `.venv-gemma4` | `rl-distill-scripts/setup_env_gemma4.sh` | torch 2.11.0, vllm 0.25.1, transformers 5.14.1, tensordict 0.13, no flash-attn | All Gemma 4 work: RL, distillation, traces, evals, tests |

```bash
# Gemma 3 FSDP2 stack (one-shot, per fresh node)
bash rl-distill-scripts/setup_env.sh && source .venv/bin/activate

# Megatron / MoE stack (H100 example; B200: TORCH_CUDA_ARCH_LIST=10.0)
UV_NO_CONFIG=1 PIP_INDEX_URL=https://pypi.org/simple CUDA_HOME=/usr/local/cuda-12.9 \
  TORCH_CUDA_ARCH_LIST=9.0 MAX_JOBS=64 bash setup_megatron.sh

# Gemma 4 stack: cu130 (default, CUDA-13 driver) or cu129 (ScaleTrain p5 fleet, 12.x driver)
VENV=/tmp/.venv-gemma4 GEMMA4_CUDA_VARIANT=cu129 bash rl-distill-scripts/setup_env_gemma4.sh
```

- **Gemma 4 venv location:** most Gemma 4 scripts default to `/tmp/.venv-gemma4`, which is on local
  NVMe and wiped by a devbox restart. The RL run-file builds it there if it is missing.
  `gemma4_topk_distill_fsdp2.sh` and `resume_gemma4_26b_a4b_local.sh` default to the repo-local
  `.venv-gemma4` instead. A successful build prints `GEMMA4_ENV_CORE_OK`. On the shared devbox,
  re-apply the Ray patches in `rl-distill-scripts/patches/README.md` after every rebuild.
- **`math_verify` must import in the venv**, or rewards silently score 0. The Gemma 4 run-file
  hard-checks this.
- **`.env`:** every stack needs a repo-root `.env` (untracked) with `HF_TOKEN=...` and
  `WANDB_API_KEY=...`. Launchers source it and forward both into Ray's `runtime_env.env_vars`.
- **Editable install:** every setup script runs `uv pip install --no-deps -e .`. In the Megatron venv
  this is how vLLM discovers the native `verl_gemma3_moe` plugin (through the package entry point
  into `verl/vllm/`).

## Architecture

### `dapo/` and `rl-distill-scripts/` share files

All RL launchers run `python3 -m dapo.main_dapo`. These `dapo/` paths are **git symlinks** into
`rl-distill-scripts/`, so each pair is one file and you can edit either:

- `main_dapo.py`
- `dapo_ray_trainer.py`
- `hf_push.py`
- `__init__.py`
- `config/`

The only real files under `dapo/` are `validation_early_stopping.py` and the `_*.py` / `_*.sh`
one-off helpers. Distillation launchers instead `cd rl-distill-scripts/` and `torchrun` the
`main_*distill*.py` entry points in place.

`main_dapo.py` subclasses verl's `TaskRunner` as `DAPOTaskRunner` and swaps in `RayDAPOTrainer`. That
trainer's custom `fit()` adds trajectory saving, pre-filter accuracy, extra metrics, and validation
early stopping. Offline distillation subclasses verl's `SFTTrainer` and swaps the loss via
`set_loss_fn()`.

### Training modalities

| Modality | Entry (invoked) | Launchers | Venv |
|---|---|---|---|
| Gemma 3 RL, FSDP2 | `dapo.main_dapo` (`dapo/config/dapo_trainer.yaml`) | `gemma3_{4b,12b,27b}_it_fsdp2_20k.sh`, `gemma3_4b_pt_*_b200_1node.sh` | `.venv` |
| Gemma 3 RL, Megatron (dense + MoE) | `dapo.main_dapo --config-name=dapo_megatron_trainer` | `gemma3_4b_pt_megatron_20k.sh`, `gemma3_4b_pt_moe_*megatron*.sh` | `.venv-megatron` |
| Gemma 3 offline distillation | `main_distill_offpolicy.py` (sampled-token forward KL) / `main_full_vocab_distill_fsdp2.py` (top-k KL) | `gemma3_4b_it_distill_offpolicy.sh`, `gemma3_27b_pt_full_vocab_distill_from_4b_pt_fsdp2.sh` | `.venv` |
| Gemma 4 RL | `dapo.main_dapo`, via the run-file `scale_train/run_gemma4_pt_deepscaler_4of4strict_rl.sh` → `gemma3_pt_fewshot_math_rl.sh` | `scale_train/launch_gemma4_*.sh`, `resume_gemma4_26b_*_local.sh` | `.venv-gemma4` |
| Gemma 4 offline top-k distillation | `main_full_vocab_distill_fsdp2.py` via `gemma4_topk_distill_fsdp2.sh` | `scale_train/run_gemma4_distill_{one,queue}.sh` | `.venv-gemma4` |

Despite its name, `gemma3_pt_fewshot_math_rl.sh` is the shared RL driver for Gemma 4 too.

Gemma 3 off-policy forward-KL distillation loads pre-generated `teacher_log_probs` and
`teacher_token_ids` from parquet (`distill_dataset.py` and `forward_kl_loss.py`). The teacher data is
generated offline: `data/launch_teacher_gen.sh` runs `data/generate_teacher_data.py` and
`data/merge_teacher_shards.py` merges the shards.

### Reward scoring

Math RL and eval route through `verl/utils/reward_score/math_verify.py`.

- **Boxed-only:** it uses `LatexExtractionConfig` only, so **only `\boxed{}` answers score**; bare
  numbers do not. Boxed-only is the default, and `VERL_MATH_VERIFY_STRICT_BOXED=0` restores lenient
  grading.
- **Which box is graded:** a response with no `\boxed{}` scores 0. With several boxes, only the
  **last well-formed** one is graded, so a model can correct an earlier answer.
- **Fallback:** a response passes if `math_verify` accepts it or a bounded Miles-style SymPy
  fallback (`miles_sympy.py`) does.
- **Routing:** `verl/utils/reward_score/__init__.py` routes `math`, `math_dapo`, `math500`,
  `olympiadbench`, `minervamath`, `gsm8k`, `beyondaime`, and any `aime*` source to it. It returns
  `{"score", "acc", "pred"}`, and `pred` feeds verl's maj@N machinery.
- **Gemma 4 evals use this same `compute_score`**, so their eval numbers equal the reward.

### Fork changes in verl

Prefer adding behavior in `dapo/` or `rl-distill-scripts/`, but the fork does edit verl core.
`git log --author=jason.wei -- verl/` lists those commits. The main areas:

- **`verl/trainer/distillation/`** holds the distillation loss registry in `losses.py`
  (`forward_kl_topk`, `reverse_kl_topk`, `reverse_kl_student_topk`,
  `reverse_kl_student_topk_bucket`) and the FSDP in-actor teacher in `fsdp/teacher_in_actor.py` and
  `fsdp/losses.py`.
- **`verl/workers/engine/fsdp/transformer_impl.py`** carries the Gemma 4 handling:
  - a cuDNN SDPA switch: `VERL_GEMMA4_CUDNN_SDPA` (default 1), with `VERL_GEMMA4_EVAL_CUDNN_SDPA`
    overriding it in eval mode;
  - installation of `verl/models/transformers/gemma4_router_replay.py`;
  - the in-actor teacher hooks.
- **`verl/utils/reward_score/`** has the routing and boxed-only scoring described above.
- **`verl/trainer/ppo/ray_trainer.py`** logs per-sample `response_length` in validation and wires up
  the distillation teacher.
- **Smaller edits** cover checkpoint managers (incl. `verl/utils/checkpoint/gemma4_checkpoint.py`),
  rollout servers, FSDP utils, and the `verl/vllm/` Gemma 3 MoE plugin.

Editing `verl/trainer/config/*.yaml` requires regenerating `_generated_*.yaml` with
`scripts/generate_trainer_config.sh`. Pre-commit verifies this.

## Gemma 4 rules

### RL

Choose the model with `GEMMA4_MODEL=google/gemma-4-{E2B,E4B,12B,26B-A4B}` and the band with
`DIFFICULTY_DATASET_SOURCE=gemma4_26b_bands DIFFICULTY_DATASET=easy|medium|hard`.

**Correctness settings are hard-coded in the run-file; change them there, not through launcher
overrides:**

- FSDP wrap class: `Gemma4TextDecoderLayer`, or `Gemma4UnifiedTextDecoderLayer` for 12B.
- `attn_implementation=sdpa` and `use_remove_padding=False`.
- Chunked entropy plus entropy checkpointing, set on both `actor` and `actor.fsdp_config`. Without
  them, step 1 runs out of memory on logits.
- An 8192 MB weight-sync bucket.
- An explicit `max_model_len`.
- `TRITON_ATTN` rollout attention with the FlashInfer sampler off.
- Token-level TIS, appended last so overrides cannot remove it.

**Router replay:**

- **26B-A4B requires `ROUTER_REPLAY_MODE=R3`.** The run-file FATALs without it, and also FATALs if
  R3 is used on a dense model.
- This is the opposite of the Gemma 3 MoE rule below, where R2 is the default.
- `ROUTER_Z_LOSS_COEF` must be 0 (not implemented).

**Validation early stopping** (`dapo/validation_early_stopping.py`):

- Enable it with `EARLY_STOPPING_ENABLED=True`, which emits `++trainer.early_stopping.*`. Nothing is
  set in the yaml.
- Its state lives in `global_step_N/validation_early_stopping.json`.
- Resume refuses a changed config unless you set `EARLY_STOPPING_MIGRATE_PATIENCE_FROM=<old>`.
- When it triggers, the best step's `actor/huggingface` must still exist locally or on S3.

### Offline top-k distillation (order matters)

1. **Generate traces:** `scale_train/run_gemma4_bestckpt_trace_collection.sh` runs
   `data/generate_gemma4_distill_traces.py` (vLLM top-128). Teachers must load the native unified
   architecture. **Trace v1 is contaminated; never use it** (ledger §2).
2. **Validate:** `data/validate_gemma4_distill_traces.py` writes `COMPLETE.json`.
3. **Build the training view:** `data/build_gemma4_distill_training_view.py`.
4. **Preflight:** the launcher runs the `data/preflight_*.py` that matches the index `schema_version`.
5. **Train:** `gemma4_topk_distill_fsdp2.sh`. Its contract:
   - `MODEL_DTYPE=fp32` master weights with BF16 FSDP param views and FP32 reductions;
   - `CLAMP_MIN_TOPK_KL=false`;
   - microbatch 1 with 4096 padded-token chunks;
   - cuDNN SDPA on for training and off for validation (`VERL_GEMMA4_EVAL_CUDNN_SDPA=0`).

   `supervise_gemma4_topk_distill.py` restarts after infra failures but stops on numerical
   failures.

The older overlay path's rescorer, `data/rescore_gemma4_training_topk.py`, is marked **"DO NOT RUN
without explicit approval"** in `data/GEMMA4_TRAINING_TOPK_RESCORER.md`.

### On-policy distillation

`ONPOLICY_DISTILL_LOSS_MODE` sets `distillation.distillation_loss.loss_mode`.

- `reverse_kl_topk` and `forward_kl_topk` use a colocated vLLM teacher.
- `reverse_kl_student_topk[_bucket]` run a frozen bf16 HF teacher inside the actor update. These
  modes are FSDP only, and the teacher servers are skipped.

What happened with each mode:

- `reverse_kl_topk` collapsed (§9.0d).
- Plain `reverse_kl_student_topk` flattened (§9.0e).
- **`reverse_kl_student_topk_bucket`** is the launcher default and the stable one (§9.0f).

### Evaluation

`scale_train/run_gemma4_rl_distill_eval_one_model.sh` evaluates one model; it is queued by
`run_gemma4_distill_study_eval_queue.sh`. The steps:

1. Read the source registry in `config/gemma4_*_eval_sources.json`.
2. `data/materialize_gemma4_eval_models.py` pins immutable revisions and SHA256 identities.
3. Run math pass@k, mean@k and maj@k: `run_gemma4_math_4gpu.py` → `eval_math_passk.py`, with
   metrics from `gemma4_eval_metrics.py`.
4. Run OOD evals: `run_gemma4_ood_4gpu.py` → lm-eval.
5. Write `RUN_COMPLETE.json`. Finished models are skipped, so the queue is safe to restart.

The math scorer is the RL reward itself, but OOD uses lm-eval's scorer, so **don't compare numbers
across the two**.

## Running jobs and storing checkpoints

### ScaleTrain (single-node EKS jobs)

- **Flow:** a `scale_train/launch_*.sh` script runs on the devbox and calls
  `launch_st_with_code.sh`, and the pod then runs `run_*.sh`.
- **Commit before launching.** Code ships as a `git archive HEAD` tarball on S3, so uncommitted
  changes are not in the job.
- **`--run-file`** is a bare filename relative to `scale_train/`.
- **Dry runs:** `launch_st_job.py --dry-run` prints the job without launching it.

```bash
cd rl-distill-scripts/scale_train
bash launch_st_with_code.sh --gpus-per-instance 4 --priority high --active-deadline-hours 72 \
  --run-file run_X.sh --job-name NAME --env-vars "K=V,K2=V2"
```

`supervise_borrowing_job.py` runs in tmux and relaunches after preemption until S3 completion
markers exist.

- It must confirm a cancel before resubmitting, so two jobs never write one checkpoint prefix.
- A suspended Kueue Job counts as queued, not completed.

### Storage rules

- **Never put checkpoints, Ray temp, the HF cache, or datasets on EFS/NFS.**
  - `assert_local_fs.sh`, sourced by the run-files, fails the launch if you do. On 2026-09-15 a
    134 GB save there stalled the whole shared devbox.
  - Use local NVMe (`/tmp` on the devbox) with S3 as the durable copy. `ALLOW_NFS_CHECKPOINTS=1` is
    for tiny smoke runs only.
  - Some older docs still say `CKPTS_DIR=$HOME/...`; the guard rejects that.
- **S3 checkpoints:** `full_checkpoint_s3.py` handles upload, rolling saves, `restore-latest` and
  `publish-best-hf`.
  - A checkpoint is valid only once `_REMOTE_COMPLETE.json`, which is uploaded last, exists.
  - S3 writes need `AWS_PROFILE=ml-worker` because the instance role is read-only. Local Ray runs
    must forward it via `+ray_kwargs.ray_init.runtime_env.env_vars.AWS_PROFILE`.
  - Pods cannot delete from S3, so prune rolling checkpoints from the devbox with
    `prune_rolling_checkpoints.sh` (run with `DRY_RUN=true` first).
- **Resharding:** FSDP checkpoints resume only at the same world size. `reshard_fsdp2_checkpoint.py`
  reshards on CPU, bit-exact; write its output to a new S3 prefix so different world sizes never
  mix.

### Checkpoint layout and resume

- **Layout:** a `SAVE_FREQ` save writes `global_step_N/{actor,actor/huggingface,data.pt}`.
  `save_contents` includes `hf_model`, a weight-only HF snapshot for inference. Resume
  `load_contents` uses only `model`, `optimizer` and `extra`, so `huggingface/` is **not** an Adam
  checkpoint.
- **Exact resume:** `RESUME_MODE=resume_path trainer.resume_from_path=<STEP_DIR>`. Keep data paths,
  shuffle seed, batch size, response count and DP layout unchanged, and make sure `data.pt` exists.
- **HF Hub upload** runs only on local-save steps. Set `HF_PUSH_ENABLE=True` and `HF_PUSH_REPO=...`,
  and make `HF_PUSH_FREQ` a multiple of `SAVE_FREQ`.

### Shared devbox

`local_jobs/` and the `*_local*.sh` resume scripts are one-off runners written for the original
author's machine. Adapt them before running:

- They hardcode `/mnt/efs/jasonwei/rl-distill`.
- In `local_jobs/resume_gemma4_12b_medium_local4.sh`, a GPU guard **kills any non-`jasonwei`
  process on its GPUs** unless `GUARD=0`.

## Gemma 3 dense→MoE workflow (read `GEMMA3_MOE_RL_TRAINING.md` first)

The most important rule: **do not start a long MoE run until validation gates A–D pass.**

1. **Convert** dense → MoE with `gemma3_moe_hf/create_gemma3_moe_from_dense_hf.py`.
   - It copies each dense MLP into every expert and adds a deterministic random router.
   - It writes two outputs: a **sparse** checkpoint for training, and a **canonical** view
     (expert 0 over the full batch) for exact tests only. **Never train the canonical view.**
   - It must print `GEMMA3_MOE_CHECKPOINT_VERIFIED`.
2. **Pass the gates.** All must match exactly, not to 99%:
   - A, HF layerwise parity: `check_gemma3_dense_moe_activations.py` → `HF_DENSE_MOE_ACTIVATION_PARITY_OK`
   - B, Megatron actor parity at prod topology: `check_gemma3_mcore_dense_moe_activations.py` → `MCORE_DENSE_MOE_ACTIVATION_PARITY_OK`
   - C, native vLLM parity: `diagnose_gemma3_vllm_parity.py` → `NATIVE_VLLM_DENSE_MOE_PARITY_OK`
   - D, bounded end-to-end RL round trip: `gemma3_4b_pt_moe_megatron_correctness_1node_h100.sh`
3. **Keep the runtime defaults.** These are correctness settings, not tuning knobs:
   - `ROLLOUT_MODEL_IMPL=native`. The generic vLLM Transformers backend is diagnostic only: it
     produced entropy ≈9 and responses that never terminated.
   - `ROLLOUT_ATTENTION_BACKEND=TRITON_ATTN`.
   - `ROUTER_REPLAY_MODE=R2`.

   Entropy near 9, or generations hitting `MAX_RESPONSE_LENGTH`, is a **correctness alarm**. Never
   hide it by tuning entropy coefficients or response limits.

Router replay modes:

- **R2** is the supported default for real runs: routes are recorded in the actor's old-logprob pass
  and replayed for the update.
- `disabled` is diagnostic.
- **R3** has vLLM capture the generation routes. It is experimental for Gemma 3 and needs
  `ALLOW_EXPERIMENTAL_R3=True`. A guardrail raises on an all-zero replay map instead of silently
  routing every token to expert 0.

The Megatron venv forces a **fresh single-node local Ray** (`RAY_ADDRESS=local`, isolated
`_temp_dir`), so it never attaches to a long-lived FSDP2-venv Ray cluster. Attaching would spawn
workers in the wrong interpreter and fail with `AssertionError: Unknown backend: megatron`.

```bash
# Gemma 3 MoE: known-good one-node 2E H100 recipe, after the gates pass
UPCYCLED_MOE_DIR="$MOE_DIR" bash rl-distill-scripts/gemma3_4b_pt_moe_2e_megatron_rl_1node_h100.sh
```

## lm-evaluation-harness

The harness is an unmodified upstream submodule that runs standalone with its own install.
**Treat it as a vendored tool:** don't hand-edit it to fix bugs, since local edits to a vanilla
clone are easy to lose and hard to review; send fixes upstream. Repo-specific tasks live outside
it, in `rl-distill-scripts/lm_eval_tasks/`; load them with `--include_path`.

```bash
cd lm-evaluation-harness && pip install -e ".[vllm]"   # the base package doesn't bundle torch/transformers
lm_eval --model vllm \
  --model_args pretrained=/path/to/checkpoint/huggingface,dtype=bfloat16,gpu_memory_utilization=0.9 \
  --tasks aime,gsm8k --batch_size auto
```

The harness's answer extraction differs from this repo's `\boxed{}`-only `math_verify`. Numbers in
`EVAL_RESULTS.md` come from the repo's own scorer, so check which scorer produced a result before
comparing.

## Gotchas

- **Gemma 3 only:**
  - Always use `sp_size=1`. Gemma 3 loads as a VLM, and the sequence-parallel path has a
    `temperature_rmpad` shape bug.
  - Set the FSDP wrap explicitly with
    `wrap_policy.transformer_layer_cls_to_wrap=["Gemma3DecoderLayer"]`; auto-discovery fails for the
    VLM.
  - `transformers` must be 4.57.6 in `.venv`, because 5.x breaks vLLM 0.15.1's `rope_scaling`
    check.
- **Ray shutdown:** use only `ray stop --grace-period 30`; `--force` breaks `/proc`.
- **NCCL interface:** single node uses `NCCL_SOCKET_IFNAME=lo` / `AF_INET`; multi-node uses
  `bond0` / `AF_INET6`.
- **Megatron on B200:** quote `TORCH_CUDA_ARCH_LIST="10.0"`. Unquoted, Hydra coerces it to a float
  and megatron-core's import-time JIT crashes.
- **Shell launchers:** don't pipe into `head` under `set -o pipefail`. It caused silent launch
  failures in the GPU pickers.
